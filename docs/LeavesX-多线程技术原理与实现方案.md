# LeavesX 多线程技术原理与实现方案

## 目标

LeavesX 的目标是在保持 Paper、Bukkit、Leaves 和原版机制兼容的前提下，把可以证明为“纯计算”的工作分配到多个计算线程。

这里的“兼容”包括：

- 实体真实 Tick、Brain、村民恐慌、村民工作与刷铁逻辑仍由服务器线程执行。
- TNT、红石、活塞、方块更新、区块写入和 Bukkit/Paper 事件回调不移到异步线程。
- 实体、世界、插件对象的线程语义不改变，插件不需要改成 Folia 插件。
- 发生线程池繁忙、任务拒绝或计算异常时，自动回到一次完整的主线程计算，不混用半成品结果。

LeavesX 因此不是 Folia 的区域线程模型。Folia 改变了世界状态的所有权和插件线程契约；LeavesX 保留 Paper 的单一世界状态所有权，只并行化安全的快照计算。这样性能上限低于彻底区域化，但兼容性和生电特性风险显著更低。

## 核心数据流

```text
服务器线程读取实时状态
        |
        v
不可变快照（基本类型数组、索引、计数）
        |
        +--> LeavesX Compute Worker 线程：距离、AABB、排序、计数
        |
        v
服务器线程等待并合并确定性结果
        |
        v
服务器线程提交实体/区块/事件状态变化
```

工作线程只能看到调用方创建的私有数组和不可变参数。它们不能通过快照反查实体，也不能调用 Bukkit、世界对象或插件代码。

## 线程分层

### 服务器线程

负责所有有副作用的操作：实体 Tick、AI 行为执行、路径结果应用、碰撞、红石/TNT、区块状态提交、事件调用和插件任务。主线程也会在等待计算线程时帮助执行未领取的纯计算分片，避免自己空等。

### LeavesX 计算线程

共享一个有界线程池，默认根据 CPU 数量自动选择并保留系统余量，最多 24 个自动线程。线程池使用守护线程、固定核心数量和有限队列，避免计算任务无限堆积。

当前可并行的工作类型：

| 工作类型 | 线程内容 | 主线程提交内容 |
| --- | --- | --- |
| AI 目标排序 | 坐标快照上的距离键、稳定基数排序 | 将稳定索引应用到实体列表 |
| AI 目标选择 | 每个分片计算最近候选索引 | 根据索引读取实体并做可见性/事件判断 |
| 实体激活范围 | AABB 基本数值相交判断 | 写入 `activatedTick` |
| 自然刷怪统计 | 快照计数和局部计数合并 | 应用刷怪上限与生成决策 |
| AI 排序归并 | 私有排序缓冲区的分片归并 | 使用完整排序结果 |

光照、网络包、票据和容器等其他优化主要是同步的分配、缓存或批处理优化，不会把世界写操作异步化。

### LeavesX 通用异步线程

刷怪统计等异步计算使用有界通用线程池。1.1.0-beta2 默认从现有线程预算划分少量区块打包线程并分开队列，避免进服、传送时的打包积压拖住其他计算；不会因此增加总线程预算。通用池会扣除 LeavesX 原有纯计算池占用的核心，为服务器线程、网络和 GC 保留余量。

实时寻路的 NodeEvaluator 依赖生物和区块状态，仅对 PathFinder 排队加锁不能保证线程安全。本轮将该入口恢复为主线程执行；AI 坐标快照上的距离与目标排序仍可并行，诊断中会区分两者。

玩家数据写入是 I/O 任务，不与 CPU 计算争抢同一队列，因此使用独立的有界 I/O 池。

### Folia 归属调度

LeavesX 只借鉴 Folia 的“任务跟随归属”原则，不引入 Folia API 或区域 Tick 线程：

- 同一归属的私有任务严格 FIFO。该机制不授权后台读取实时生物或区块，实时寻路目前在主线程执行。
- 同一 UUID 的玩家存档严格串行，不同玩家的磁盘写入可以并行。
- 同一归属有任务时只有一个排空器进入线程池，无任务后立即移除归属记录，不保留实体或玩家强引用。
- 队列有界；顺序敏感任务在满载时施加背压，不会用 caller-run 越过已排队任务。

这里的“归属”只保护已审计的私有计算器或存档键。给活世界对象加锁后在后台修改它，仍然会破坏 Paper/Bukkit 线程契约，所以没有纳入通用调度。

## Leaf parallel-world-ticking 的边界

Leaf 的 `parallel-world-ticking` 来自 SparklyPaper，是实验性的“按世界并行 Tick”：主世界、下界和末地可以同时推进，但单个世界内部仍不是 Folia 的区域多线程。它需要为每个世界建立 Tick 所有权，并额外处理跨世界传送、容器、区块读写和插件全局状态。

LeavesX 当前不引入该模型。原因不是线程池本身，而是 Bukkit/Paper 插件普遍假设所有世界任务都在同一个服务器线程上。只给世界 Tick 加锁不能修复插件共享容器、跨世界传送和静态缓存的竞态。在不改变插件线程契约的前提下，LeavesX 继续只并行已冻结的计算、编码和 I/O。

## 调度算法

### 分片

一个输入数组被拆成连续、确定性的范围。分片数量不超过计算线程数的两倍，并受 64 个分片上限约束。每个分片只写自己的输出区间，因此不需要锁。

每次调用保留最后一个分片给调用线程；其他分片优先交给空闲计算线程。调用线程仍会领取未开始的尾部分片，避免慢线程造成长尾。

### 自适应准入

大批次达到配置阈值时直接并行。对于已审计的 AI、实体激活和刷怪统计工作，当线程池空闲且输入达到阈值的一半时，也允许并行。

实体距离排序和最近目标查询同样使用这一规则：中等规模候选集会先做坐标快照，再使用纯数组计算，不再因为没有达到硬阈值而固定单线程。

线程池繁忙时不再盲目排队新的批次。调用线程会完成这批快照计算，并在诊断统计中记录回退原因，避免队列堆积造成 MSPT 突刺。

### 争用与尾部处理

- 任务提交前原子预留空闲线程槽位，多个同时到达的快照不会重复占用同一批线程。
- 一个队列任务可以领取少量连续分片，降低队列锁和提交开销。
- 接近尾部时自动缩小领取宽度，减少一个线程拿走全部尾部后其他线程空闲的情况。
- 主线程采用短自旋加 250 微秒限时等待，兼顾短任务延迟和 CPU 占用。
- 计算线程再次调用计算线程池时改为当前线程内联执行，防止固定线程池嵌套等待死锁。

## 异常与兼容回退

每个分片独立捕获异常并记录失败。调用线程会等待已经提交的全部分片结束，然后从同一个不可变快照重新执行完整的同步计算。这样不会把“部分并行、部分同步”的排序或计数结果交给游戏逻辑。

线程池关闭或队列拒绝时，只在调用线程执行尚未完成的范围；已完成范围不会重复计算。所有失败、拒绝、队列争用和主线程帮助统计都可通过诊断命令查看。
