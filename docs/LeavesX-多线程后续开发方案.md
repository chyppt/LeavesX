# LeavesX 多线程后续开发方案（1.1.0-beta6 起）

本文是《LeavesX-多线程技术原理与实现方案》的续篇，规划 beta5 之后的并行化路线。适用分支 `leavesx/26.1.2`，补丁序号从 0308（paper 侧 0229）继续，配置版本从 80 递增。

## 一、现状与差距

已并行（beta5 及之前）：

| 路径 | 状态 |
| --- | --- |
| AI 目标排序 / 目标选择 / 归并 | 已并行，默认开启 |
| 实体激活范围 AABB | 已并行，默认开启 |
| 自然刷怪统计 | 已并行，默认开启 |
| 实体追踪差量计算 | 已并行，默认开启 |
| 区块打包 / 发送（含队列隔离） | 已并行，默认开启 |
| 玩家存档采集后压缩与写盘 | 已并行，按 UUID 串行 |
| 长跳候选 / 冲撞筛选 / 跳跃候选 | 已并行，默认开启 |
| 水中寻路完整搜索（快照） | 实验性，默认关闭 |
| 生物简单碰撞盒数学 | 实验性，默认关闭 |

主线程剩余热点（按典型高实体/高区块负载的 MSPT 占比排序）：

1. **陆地寻路**：水中寻路已快照化，陆地 NodeEvaluator 仍在主线程，是大型生物群服最大的单项 AI 开销。
2. **高密度实体推挤**：目前只并行了查询与有界计算，推挤增量的完整求解仍在主线程，掉落物堆叠和刷怪塔场景受限。
3. **区块存档序列化**：自动保存尖峰的主要来源之一，序列化仍在 Tick 线程。
4. **爆炸射线计算**：TNT 阵列场景下纯数学占比高，但生电对确定性要求最严格。
5. **光照引擎批处理**：已同步批处理，是否值得并行需要测量结论。

已明确放弃的方向维持不变：Folia 区域化、parallel-world-ticking、异步 Bukkit 事件、异步实体/区块状态写入、村民与 TNT/红石路径异步化。

## 二、不变的约束

每个里程碑都必须满足以下条款，任何一条不满足即整项回退，不发布：

1. 数据流固定为「主线程读取实时状态 → 构建不可变快照 → 计算线程纯数学 → 主线程合并确定性结果 → 主线程提交副作用」。
2. 线程池繁忙、队列拒绝、快照越界、计算异常时，从同一快照完整同步重算，不混用部分结果。
3. 计算线程不接触 Bukkit API、世界对象、实体对象和插件代码。
4. 新增并行路径一律先以 `experimental` 命名空间 + 默认关闭发布，连续两个 beta 无回退问题后再评估默认开启。
5. 与原算法的对拍测试（节点、顺序、代价、计数逐项一致）是合并前置条件。

## 三、里程碑

### M1 调度分级与快照预算（先行，一个 beta 内完成）

问题：当前共享计算池对所有任务一视同仁。寻路采用发生在 Tick 内（主线程短自旋等待），而刷怪统计、追踪差量可以晚一拍；队列拥堵时互相拖累。水中快照有 16 个内存名额，其他快照类型各自为政，极端负载下没有全局内存上界。

内容：

- **优先级车道**：`tick-critical`（主线程正在等待：寻路采用、激活范围、AI 排序）与 `best-effort`（可延后一拍：刷怪统计、追踪差量、长跳候选）分队列；线程池饱和时 best-effort 进延后重试队列，不与 tick-critical 抢占线程槽。复用 0216 已有的延后重试机制。
- **快照预算治理**：把水中快照的「名额」推广为全局快照内存 watermark，所有快照类型统一记账；超过预算时新请求直接同步计算并计入诊断，防止多特性叠加时 OOM。
- **诊断 v2**：按类别暴露队列深度、回退原因直方图、快照内存占用；为关键回退路径增加 JFR 事件（可选开关）。

验收：注入式压力测试（线程池打满 + 快照名额耗尽 + 异常注入）下无死锁、无部分结果；现有全套回归通过；`/leavesx threads` 输出新指标。

配置：`parallelism.priority-lanes`（默认 true）、`parallelism.snapshot-memory-budget-mb`（默认 64）。

### M2 地面寻路快照（旗舰，beta6 核心）

水中寻路已验证「快照 + 后台完整搜索 + 采用前复核」框架可行。陆地寻路复用同一框架，难点在于 GroundNodeEvaluator 的输入面更宽。

冻结清单（主线程在快照构建时一次性完成）：

- 区块段压缩方块数据（同水中，49×49×49，最多 64 段）；
- 流体标签分类（复用 beta5 的标签冻结）；
- PathType 分类表：BlockState → PathType 在主线程预计算并冻结，工作线程只查表，不调用 `getBlockPathType` 实时逻辑；
- 门/活板门开闭状态（属于方块状态，随快照冻结）；
- 天光/方块光 nibble 快照（僵尸等日晒规避生物需要；无此类生物时不采集）。

排除路径（走原流程，不尝试并行）：被栓绳牵引、处于载具中、自定义 Navigation/NodeEvaluator 子类、开启寻路调试采集、`EntityPathfindEvent` 被监听且结果依赖实时状态、快照范围内存在动态代价源（活跃 TNT、掉落中的方块实体）。

采用前复核与水中一致：请求归属、生物状态、实际读过的方块、分类失效条件；任一不符即完整重算。

验收：对拍矩阵覆盖平地/楼梯/门/栅栏/水陆交界/日晒规避/负坐标/不同体型与 malus，逐节点一致；真实服对照开启/关闭各 48 小时；`land-snapshot` 下 `PathFinder` 主线程调用计数趋近于排除路径数。

配置：`async.pathfinding.land-snapshot`（默认 false，复用 threads/queue-size/keepalive）。

### M3 整 Tick 共享实体快照

问题：激活范围、AI 目标、追踪差量、碰撞查询各自构建快照，同一 Tick 内重复读取同一批实体字段，快照成本随消费方数量线性增长。

内容：每 Tick（或每 N Tick，按实体规模自适应）在主线程构建一次基础实体快照（位置、AABB、类型索引、激活标志的 primitive 数组），各消费方在其上做自己的投影，不再重复遍历实体列表。与 0297/0299 已有的激活快照共享和 tracker player frame 共享合并为统一设施。

契约不变：所有消费方容忍「Tick 起点数据」，与现在的 per-call 快照语义相同，只是更便宜。快照构建本身在实体数低于阈值时自动退化为 per-call，避免小服白付构建成本。

验收：各消费方结果与 per-call 快照 bit-exact；快照构建总耗时计数低于原先各消费方快照之和。

配置：`parallelism.shared-entity-snapshot`（默认 true，阈值 `minimum-entities` 默认 1024）。

### M4 高密度实体推挤完整并行

现状：0302 有界查询 + 0306 实验性碰撞数学只覆盖部分计算。本里程碑把推挤增量完整求解移到计算线程。

方法：快照全部参与者的 AABB 与质量参数（复用 M3 共享快照）；pair 按「分片内有序对」划分，每对独立计算推挤增量（纯数学）；合并阶段在主线程按实体索引序累加并应用，保证与串行遍历相同的累加顺序。掉落物合并扫描同法。

排除：村民、TNT/爆炸相关实体、复杂碰撞形状、任何监听了 `EntityCombustByEntityEvent` 等推挤相关事件的场景（有监听器即整批回退主线程，保证事件时序不变）。

验收：推挤结果（位移增量、顺序）与串行一致的对拍测试；2 万掉落物堆叠场景 MSPT 对比报告；生电掉落物合并行为（合并数量、位置）不变。

配置：`parallelism.entity-push-resolution`（默认 false，experimental）。

### M5 区块存档序列化下线程

自动保存尖峰来自 Tick 线程上的 NBT 序列化。方法：主线程在存档锁内冻结区块状态引用（复用既有 autosave 流程的排空语义）→ 计算线程序列化 NBT → 既有 I/O 池写盘。POI 与实体区块一并纳入。与区块打包共用 I/O 线程预算，不新增总线程数。

验收：存档一致性（重启后区块逐字段比对）；自动保存期间 MSPT p99 对比；崩溃注入测试（序列化中途宕机不产生半成品文件，落回下次重存）。

配置：`async.chunk-save-serialization`（默认 true——此项不改变任何游戏逻辑，仅移动序列化时机，风险等级低于前几项）。

### M6 探索项（严格门控，不承诺合并）

- **爆炸射线并行**：快照方块状态与抗性表，射线独立计算暴露度；RNG 按射线序号派生固定子种子保证序列可复现；合并按原顺序。生电 TNT 装置（炮、复制机）bit-exact 验收不达标即放弃，永不默认开启。
- **光照分层并行**：先用 M1 诊断测量光照批处理实际占比，低于阈值（如 MSPT 3%）直接关闭该项。

## 四、并行工程轨道（贯穿所有里程碑）

1. **对拍框架产品化**：把「异步结果 vs 同步结果逐项一致」做成可复用测试设施，新并行路径接入成本降到一次注册。
2. **脚本化基准**：固定场景（2k 生物平原、10k 掉落物堆叠、传送风暴、TNT 阵列、自动保存窗口）输出 MSPT p50/p99 报告进 `build/reports`，每个 beta 留档对比；只报告实测，不承诺提升百分比。
3. **真实服 soak**：每个 experimental 项至少一个 beta 周期的真实服运行，回退计数为 0 才能转默认开启。
4. **发布节奏**：M1 → beta6（含 M2）→ beta7（M3+M4）→ beta8（M5）→ 1.1.0-rc（默认值翻转 + 全量回归 + 文档）。
